# v0.2 API specification

Status: **Released in v0.2.0; maintained for v0.2.x**

This document is the normative contract for the supported v0.2 release line. The superseded v0.1.0 contract remains in `v0.1-api.md` for migration and historical compatibility reference.

## Goals

v0.2.0 is a security-only release. It must preserve Singleserve's loopback hosting, application-handler composition, browser presence, lifetime, shutdown, and framework-neutral client outcomes while ensuring that browser authentication capabilities are never persisted in script-readable storage or exposed to consumer JavaScript.

## Public Go surface

The public package remains `github.com/rztaylor/singleserve`. The v0.1 server, lifetime, guard, tab, opener, result, and launch methods remain except where this specification changes their behavior.

```go
const (
    TokenHeader = "X-Singleserve-Token"
    TabHeader   = "X-Singleserve-Tab"
    ControlPath = "/_singleserve/"
)

func (l *Launch) Client() *http.Client
func (l *Launch) NewBootstrapURL() (string, error)
```

`Launch.Client` returns a programmatic client bound to that launch. It:

- carries an independent 256-bit programmatic credential in `TokenHeader` without exposing the value;
- refuses requests and redirects whose scheme or host differ from `Launch.BaseURL()`;
- bypasses environment HTTP proxies so a local credential cannot be disclosed to a proxy;
- dials the bound loopback listener directly while retaining the isolated request origin, avoiding a dependency on operating-system `.localhost` DNS behavior; and
- does not create browser-tab state unless the caller explicitly supplies a valid `TabHeader` to a tab endpoint.

A nil `Launch` returns nil. Callers that need application-specific transport behavior may wrap the returned client at their own boundary but cannot extract the credential from Singleserve.

Direct `Authorization: Bearer` authentication is removed. `TokenHeader` remains the documented programmatic wire mechanism and is set by `Launch.Client`.

## Listener and launch origin

- Empty `Options.Address` remains `127.0.0.1:0`.
- Supported hosts are `127.0.0.1`, `::1`, and `localhost`, with any valid port including `0`. Other loopback aliases are rejected because they cannot participate reliably in the isolated browser-origin contract.
- The TCP listener binds the normalized address. Browser and programmatic URLs use an independent, high-entropy host of the form `ss-<128-bit-lowercase-hex>.localhost` with the assigned listener port.
- Every HTTP request must carry the exact launch host and port, compared case-insensitively. Missing, malformed, aliased, trailing-dot, or otherwise different `Host` values return 421 before authentication or application delegation.
- `Launch.Address()` returns the actual listener address. `Launch.BaseURL()` returns the isolated clean origin ending in `/`.

The high-entropy hostname isolates the host-only session cookie from ordinary sibling loopback origins such as `127.0.0.1`, `localhost`, or another Singleserve launch. Knowledge of the full launch hostname remains capability-adjacent information and must not be logged independently of the explicit bootstrap URL.

## Independent credentials

Each `Server` initially generates independent values from `crypto/rand`:

- a 256-bit one-time browser bootstrap capability;
- a 256-bit browser-session cookie value;
- a 256-bit programmatic client credential; and
- a 128-bit launch-host label.

Failure to generate any initial value fails construction. Every successful `Launch.NewBootstrapURL()` call draws another independent 256-bit bootstrap capability; renewal entropy failure leaves the active capability unchanged. Values are never derived from one another, persisted, logged, or returned to application handlers.

## Browser bootstrap

`Launch.URL()` returns:

```text
http://ss-<launch>.localhost:<port>/_singleserve/bootstrap#<bootstrap-capability>
```

The fragment keeps the capability out of the HTTP request target, server logs, caches, and referrers. Treat the complete URL as a secret until bootstrap succeeds.

The initial bootstrap expires two minutes after `Start` and is atomically consumed by the first successful exchange. The flow is:

1. `GET /_singleserve/bootstrap` serves only a fixed Singleserve-owned HTML document.
2. That document loads `GET /_singleserve/bootstrap.js` under a restrictive Content Security Policy.
3. The script copies the fragment into a closure, immediately removes it with `history.replaceState`, and sends it in `X-Singleserve-Bootstrap` on `POST /_singleserve/bootstrap` with same-origin credentials.
4. The server requires the exact launch Origin, validates and consumes the capability, sets the browser-session cookie, and returns success.
5. The script uses `location.replace("/")`, so consumer HTML and JavaScript first run at the clean base URL.

The bootstrap GET and script are unauthenticated only at the exact high-entropy launch Host and disclose no capability. A missing, invalid, expired, or consumed capability receives the same generic 401 response. A browser already holding the current valid session cookie may repeat the exchange so revisiting the original URL in the same browser recovers cleanly; a different browser cannot reuse the consumed URL.

`Launch.NewBootstrapURL()` is the owner-controlled recovery primitive. It generates a new independent 256-bit capability, immediately invalidates the earlier unconsumed capability, resets the bootstrap deadline to two minutes from the successful call, updates `Launch.URL()` to the newly issued URL, and returns that URL. It does not change lifetime policy, first-contact policy, tab state, the browser-session credential, or an already established browser session. Entropy or URL-construction failure returns an error and leaves the current capability and deadline unchanged. Calling it on a nil or stopped launch returns an error. Concurrent calls are serialized; only the most recently issued unconsumed capability remains valid.

If a renewed URL is opened in the existing failed bootstrap tab, the browser may treat only its fragment as a same-document navigation. The fixed bootstrap page listens for that fragment change, repeats the same immediate closure-and-scrub sequence, and exchanges the renewed capability without loading consumer code or retaining it in browser storage.

The API does not imply automatic renewal or a consumer UI. An explicit/manual consumer may require first bootstrap within the current two-minute window and require an owner restart after expiry. A consumer that offers renewal must invoke `NewBootstrapURL()` from its own trusted owner-control boundary and protect the returned URL as a secret.

Bootstrap responses are `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, and `X-Content-Type-Options: nosniff`. The HTML uses a CSP limited to its same-origin script and connection, with no framing, forms, objects, base changes, or external resources.

## Browser session cookie

The bootstrap exchange sets a launch-unique, host-only cookie named `__Host-singleserve_<96-bit-session-derived-id>` containing the independent session value:

- `Path=/`;
- `HttpOnly`;
- `Secure` and a `__Host-` name prefix;
- `SameSite=Strict`;
- no `Domain`, `Expires`, or `Max-Age`; and
- browser acceptance over the potentially trustworthy `.localhost` HTTP origin, even though v0.2.0 does not introduce local TLS.

The high-entropy host provides confidentiality from ordinary sibling loopback origins. The `__Host-` rules additionally prevent a related `.localhost` service from setting a parent-domain cookie with the session name. Duplicate session cookies fail authentication instead of creating cookie-tossing ambiguity. The server removes its cookie before application delegation. A process-dead cookie is useless because credentials and host labels are never reused.

## Authentication and request provenance

Outside the bootstrap resources, authentication is satisfied only by:

- the current launch's programmatic `TokenHeader`; or
- the current launch's browser-session cookie.

The server records the accepted credential mode internally.

- Every request first requires the exact launch Host.
- A malformed or mismatched browser `Origin` is rejected regardless of credential mode.
- Unsafe cookie-authenticated requests require an Origin exactly equal to `Launch.BaseURL()` without its trailing slash. Missing Origin fails closed.
- Programmatic-header requests may omit Origin. If present, it must match exactly.
- `GET` and `HEAD` are the only methods treated as safe for this rule.
- Bootstrap POST always requires exact Origin.
- No permissive CORS response is emitted.

Singleserve removes its token header, launch cookie, bootstrap header, and tab control data as applicable before consumer delegation. Application cookies and all application `Authorization` values are preserved.

## Reserved HTTP surface

All Singleserve-owned responses include `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. JSON responses use `application/json`; scripts use `text/javascript`; bootstrap HTML uses `text/html`.

| Method | Path | Authentication | Purpose |
| --- | --- | --- | --- |
| `GET` | `/_singleserve/bootstrap` | exact launch Host | Fixed bootstrap document |
| `GET` | `/_singleserve/bootstrap.js` | exact launch Host | Fixed bootstrap script |
| `POST` | `/_singleserve/bootstrap` | one-time bootstrap or existing session, exact Origin | Establish browser session |
| `GET` | `/_singleserve/health` | session or programmatic | Liveness |
| `POST` | `/_singleserve/tabs/heartbeat` | session or programmatic | Record tab presence |
| `POST` | `/_singleserve/tabs/disconnect` | session or programmatic | Record tab disconnect |
| `POST` | `/_singleserve/shutdown` | session or programmatic | Request guarded shutdown |
| `GET` | `/_singleserve/client.js` | session or programmatic | Canonical lifecycle client |

Control endpoints accept no request body, including chunked bodies. A body returns 413. Method, tab-ID, and shutdown behavior otherwise retain the v0.1 contract.

The HTTP server keeps its five-second header timeout and adds a 30-second idle timeout and 64 KiB maximum request-header limit. Singleserve does not impose a whole-request body timeout on the consumer-owned handler.

## Framework-neutral browser client

The canonical lifecycle module remains `client/singleserve.js` and is served byte-for-byte.

`connect(options)`:

- never reads or writes Web Storage, IndexedDB, Cache Storage, a service worker, or another persistent browser API;
- never reads a capability from the URL;
- returns no token and exports no token query or storage key;
- creates a cryptographically random tab ID;
- preserves the v0.1 heartbeat, observation, failure-threshold, unavailable-server, pagehide/pageshow, disconnect, stop, health, fetch, and guarded-shutdown outcomes;
- removes any caller-supplied `TokenHeader`, sets the current tab header, forces same-origin credentials, and refuses cross-origin targets; and
- never retries an application request.

Reload and clean new-tab authentication depend only on the HttpOnly session cookie.

## Browser opener

Browser URLs are always passed as a single argument without a shell or command interpreter. The WSL `cmd.exe /C start` fallback is removed. Bootstrap capability exposure in the short-lived opener argument is bounded by fragment transport, immediate scrubbing, two-minute expiry, atomic consumption, and rejection of replay without the established session cookie. An actor with permission to inspect that command line before consumption can race the browser and is outside the preventable boundary; applications may omit `OpenBrowser` and present the explicit manual URL through their own trusted UI when that local threat applies.

## Validation and release gate

v0.2.x release candidates require:

- deterministic Go and Node contract tests;
- race coverage for bootstrap consumption, authentication, tab tracking, and shutdown;
- hostile sibling-loopback and exact Host/Origin integration tests;
- a real-browser harness proving fragment scrubbing before consumer code, no Web Storage/token exposure, Secure `__Host-` cookie acceptance, reload/new-tab behavior, related-domain cookie rejection, replay rejection, and lifecycle behavior;
- vulnerability and static security analysis with reviewed tool versions;
- immutable third-party CI action references and minimal permissions;
- at least 80% Go statement coverage; and
- matching README, package docs, architecture, decisions, migration, changelog, facts, SECURITY, and release governance.

The repository-owned Playwright Chromium security gate is not skippable at the candidate commit. Its runner OS is not part of the contract, and missing local browser infrastructure does not block ordinary development.

## Migration from v0.1.0

- Remove uses of `session.token`, `TOKEN_STORAGE_KEY`, `TOKEN_QUERY`, and the browser `TOKEN_HEADER` export.
- Do not parse `Launch.URL()` for a programmatic token. Use `Launch.Client()`.
- Expect `Launch.URL()` to point at a Singleserve bootstrap resource with a fragment and `BaseURL()` to use a high-entropy `.localhost` host.
- Use `Launch.NewBootstrapURL()` only for an owner-controlled replacement of an unconsumed or expired manual URL; it resets the bootstrap window but not server lifetime.
- Remove assumptions that application HTML handles or observes the launch query.
- Do not retain or introduce a browser token-storage option.

## Explicit deferrals

The v0.1 non-goals remain: remote access, LAN mode, TLS termination, accounts, desktop webviews, service workers, WebSockets, npm, TypeScript packaging, configurable control paths, application persistence, and consumer-specific adapters.
