# ExecPlan 000 — v0.2.0 security hardening

Status: In progress. Scope was explicitly approved; runtime and automation are implemented, while real-browser/hosted evidence and release-candidate closure remain.

This is a living implementation plan. Keep `Progress`, `Discoveries`, and `Decision record` current while work is active. When the roadmap item is complete, move durable outcomes into the normative specification, architecture, decisions, migration, changelog, and release governance, then remove this plan and close the roadmap item.

## Goal

Release v0.2.0 as a security-only minor version that replaces v0.1.0's script-readable browser token lifecycle with a server-owned, isolated browser session; closes adjacent launch-capability, cookie-origin, Host/Origin, opener, and control-surface risks; and makes the browser and security evidence needed to support those claims non-skippable.

The user-visible result is that an application can call `connect()` without any Singleserve authentication capability being written to Web Storage or returned to application JavaScript. Initial launch, reload, new tabs, authenticated fetches, heartbeats, reconnect observations, disconnect, guarded shutdown, and server-unavailable behavior continue to work.

## Background and current state

`v0.1.0` is tagged at `e188c833e9ddb96dd5369165e8a7fbb742328495`. Its Go server generates one 256-bit token and reuses it as URL capability, header/bearer credential, and cookie value. A safe query-token request sets a launch-unique `HttpOnly`, `SameSite=Strict` session cookie and delegates the same response to the consumer handler. The canonical client then reads the token from `window.location`, stores it in per-tab `sessionStorage`, scrubs the query with `history.replaceState`, sends the token header, and returns the token as `session.token`.

That design has four confirmed release-blocking gaps for the next version:

1. `localStorage` and `sessionStorage` are script-readable credential stores. The token also remains publicly reachable through `session.token`.
2. Consumer HTML and any earlier-running application script execute while the token remains in the address bar; scrubbing depends on the consumer importing and calling the client promptly.
3. HTTP cookies are scoped by host, not port. Different loopback servers on `127.0.0.1` receive the same host cookies even when their ports differ. A launch-unique cookie name avoids authentication collisions but not disclosure, overwrite, accidental logging, or replay by a sibling service.
4. The release evidence does not currently include a mandatory real-browser authentication harness, vulnerability scan, static security analysis, or immutable CI action review.

The audit also identified concerns that must be resolved or explicitly disproved before release: exact `Host` validation and DNS-rebinding resistance; unsafe cookie-authenticated requests with absent or malformed `Origin`; long-lived/replayable launch capabilities exposed in browser-opener arguments; the WSL `cmd.exe /C start` fallback; strict input and body limits for reserved endpoints; HTTP connection/header resource bounds; cookie attribute behavior on supported localhost browsers; authentication failure and secret non-echo fuzz cases; credential invalidation/cleanup; and supply-chain integrity of CI actions and security tooling.

The current threat boundary trusts the Singleserve process, the selected browser implementation, and consumer code intentionally supplied as `Options.Handler`. It does not trust remote web pages, sibling loopback services, or unrelated local processes. OS administrator access, process-memory inspection, a compromised browser or extension, and arbitrary execution inside trusted consumer code are outside the preventable boundary. Same-origin XSS can still act with an HttpOnly cookie while it is executing; the goal is to prevent it from extracting a reusable Singleserve credential.

## Scope

### Normative security design

- Write `docs/dev/specs/v0.2-api.md` before runtime implementation. It must version the complete public and wire contract rather than patching the released v0.1 specification in place.
- Record the final browser bootstrap, cookie, programmatic authentication, Host/Origin, credential lifetime, and migration decisions in `docs/dev/decisions.md`.
- Preserve strict loopback-only listening and the existing consumer ownership of `http.Handler`, application routes, assets, frontend framework, domain state, and cleanup.

### Browser credential lifecycle

- Remove all `localStorage`, `sessionStorage`, IndexedDB, Cache Storage, service-worker, or equivalent persistence of Singleserve authentication capabilities.
- Remove `session.token` and any browser-client exports whose only purpose is reading or persisting the launch capability. Do not provide a legacy storage mode.
- Move URL capability consumption and clean navigation into a dedicated Singleserve-owned bootstrap response so application HTML and JavaScript only run at a token-free URL.
- Use distinct, independently generated secrets for bootstrap, browser session, and programmatic authentication wherever those roles have different lifetime or disclosure requirements.
- Make bootstrap capability lifetime and replay explicit. The preferred design is single-use or narrowly time-bounded, atomically consumed, non-cacheable, and followed by a redirect to the clean application URL. Preserve a safe manual-launch recovery path without making a consumed credential reusable indefinitely.
- Keep the final browser credential in an `HttpOnly`, `Secure`, `SameSite=Strict`, non-persistent `__Host-` cookie. Browser acceptance on the chosen loopback hostname and related-domain injection rejection are release gates; failure blocks v0.2.0 rather than weakening the attributes.

### Per-launch origin and request validation

- Replace random-port-only cookie isolation with a per-launch browser host/origin that prevents cookie disclosure to sibling loopback services. The first implementation candidate is a high-entropy host under `.localhost`, backed by RFC 6761 behavior, exact Host validation, and direct loopback listening. It must pass the canonical real-browser contract plus deterministic Go listener/address tests; a browser/OS cross-product is not required without a concrete compatibility finding.
- If `.localhost` subdomain behavior is not sufficiently interoperable, evaluate a distinct tested loopback-address origin. Do not fall back to shared-host cookies. Failure to prove an origin design blocks v0.2.0.
- Validate the effective request `Host` before authentication or consumer delegation. Reject aliases, malformed hosts, and DNS-rebinding hosts not equal to the launch origin.
- Track which credential mechanism authenticated a request. Require an exact launch `Origin` for unsafe cookie-authenticated browser requests. Permit an absent browser `Origin` only for explicit programmatic header/bearer authentication; reject a mismatched or malformed Origin regardless of credential type.
- Treat `Sec-Fetch-Site` and related Fetch Metadata as defense-in-depth signals only after browser compatibility review; never make their absence weaken the primary Host, Origin, and credential checks.
- Verify that simultaneous launches, sibling hostile loopback servers, IPv4/IPv6, `localhost`, and configured loopback addresses cannot collide or receive each other's browser session credentials.

### Opener, HTTP, and control-surface hardening

- Minimize capability usefulness if an OS browser-launch argument is observed. Prefer a one-time bootstrap capability separated from the session and programmatic credentials.
- Remove shell or command-interpreter browser-launch fallbacks, including `cmd.exe /C start`, unless a reviewed implementation can prove arguments cannot be interpreted. Continue to pass URLs as one non-shell argument.
- Add strict request-body behavior for Singleserve control endpoints, bounded header/input handling, and explicit `X-Content-Type-Options: nosniff`, cache, and referrer headers where Singleserve owns the response.
- Review `http.Server` timeout, idle-connection, and maximum-header settings against slow-header and unauthenticated resource-exhaustion attacks without imposing an application-body timeout that breaks consumer-owned handlers.
- Review authentication failure behavior, cookie parsing, duplicate credential precedence, method handling, tab-ID bounds, shutdown guards, and error responses for ambiguity, amplification, leakage, or fail-open behavior.
- Decide how browser session cookies are invalidated on browser-requested shutdown and process end without clearing unrelated localhost state. Per-launch host isolation must make stale, process-dead cookies harmless and non-disclosing.

### Security verification and release governance

- Build a repository-owned real-browser harness for bootstrap redirect, clean URL, no Web Storage, HttpOnly cookie reload, new tab, two-tab lifetime, final disconnect, cross-origin rejection, sibling-loopback cookie isolation, capability replay, and unavailable-server behavior.
- Keep Node unit tests for deterministic client scheduling and API behavior, but do not treat mocks as evidence of browser cookie or history semantics.
- Add table-driven Go auth tests, cross-service cookie tests, concurrency/race tests for atomic bootstrap consumption, and fuzz seeds for malformed Host, Origin, cookie, authorization, query, tab, and control requests.
- Add an official Go vulnerability check with a pinned tool/version and recorded database freshness for release candidates. Keep the ordinary offline check deterministic; define the networked security evidence separately rather than silently downloading during `scripts/check.sh`.
- Add static security analysis and CodeQL or a documented equivalent with minimal permissions. Pin third-party GitHub Actions to immutable commit SHAs and keep Dependabot capable of updating reviewed pins.
- Update release checks so v0.2.0 refuses to pass without the proposed v0.2 specification, browser-security result, vulnerability/static-analysis evidence, secret scan, clean worktree, and matching changelog heading.
- Correct `SECURITY.md`, document supported versions and private reporting, and state the exact local threat boundary and known limitations without claiming protection against compromised trusted components.

## Non-goals

- Remote or LAN listeners, TLS termination, account identity, multi-user authorization, desktop webviews, service workers, WebSockets, server-sent events, npm publishing, TypeScript packaging, configurable control paths, or application persistence.
- Consumer-specific SQLRise code, compatibility aliases, or application-domain shutdown behavior.
- A legacy `tokenStorage: "session"` or equivalent weaker mode.
- A general router, asset pipeline, CSP generator, browser sandbox, XSS sanitizer, or replacement for consumer security headers and application authorization.
- Defending against an OS administrator, debugger/process-memory reader, an actor permitted to inspect the short-lived browser-launch command line, compromised browser/extension, malicious code intentionally embedded by the consumer, or denial of service by an actor with equivalent control of the user account. The documentation must still describe residual effects accurately.
- Tagging, publishing, pushing, or creating a GitHub release. Those actions require separate explicit authorization after release checks pass.

## Design

The target browser flow is:

1. `Start` binds loopback and creates independent high-entropy bootstrap, browser-session, and programmatic credentials plus a per-launch browser origin.
2. `Launch.URL()` returns a dedicated Singleserve bootstrap URL, not an application URL with a reusable session credential.
3. The bootstrap endpoint validates exact Host, method, and capability, consumes or expires the capability atomically, sets the isolated HttpOnly cookie, and responds with a non-cacheable, non-referring redirect to the clean application URL.
4. The browser requests consumer HTML only after the URL is clean. The canonical ES module never reads a token and uses same-origin credentials automatically.
5. Auth middleware identifies the accepted credential mechanism, applies mechanism-appropriate Origin checks, removes Singleserve credentials, and delegates only a clean request to the consumer handler.
6. Programmatic callers use an explicit non-browser credential contract that does not require parsing or reusing the browser bootstrap URL.

This design is provisional only where browser evidence is required: the exact per-launch hostname mechanism, the programmatic credential API shape, cookie `Secure`/prefix behavior, and bootstrap reuse semantics. Milestone 1 resolves those points in the proposed v0.2 specification before implementation proceeds. Security properties are fixed; only the interoperable mechanism may change.

Package ownership remains in the root `singleserve` package unless implementation creates a demonstrated responsibility large enough for an `internal/` extraction. `Server` owns secret generation, bootstrap state, accepted origin, authentication mode, and HTTP limits. `Launch` exposes only the approved browser and programmatic integration contract. `auth.go` owns Host/Origin and credential validation. `control.go` owns the bootstrap and bounded control endpoints. `client/singleserve.js` owns lifecycle scheduling but no authentication secret. `opener.go` owns non-shell platform launch commands. Consumer handlers never know Singleserve credentials or bootstrap state.

## CLI contract

Singleserve has no distributed CLI. `go run ./examples/minimal` remains the executable public-API specification. Its printed manual URL may change to the dedicated short-lived bootstrap URL, and it must continue to avoid printing any other credential or logging the URL after its documented one-time display.

## Data and configuration changes

No application data, persistent Singleserve state, schema, environment variable, or consumer configuration is introduced. Browser session state changes incompatibly: the v0.1 Web Storage key is no longer read or written, and any stale value is ignored. The migration guide may recommend consumers remove the stale key from their own upgrade code only if doing so does not require Singleserve to read it.

No security option selects a weaker behavior. Custom `Options.Address` remains loopback-only, but the specification must define whether and how configured IP/hostname binds participate in the isolated browser origin.

## Safety and security impact

The change reduces the lifetime, reachability, and reuse of browser authentication material. It also changes the public browser-client and launch/authentication contracts, so silent compatibility is not possible or desirable.

Key invariants:

- no browser-readable persistent credential;
- no credential in returned JavaScript state;
- no consumer content at a capability-bearing URL;
- distinct credential roles and bounded bootstrap replay;
- no cookie disclosure or overwrite across mutually distrusting loopback services;
- exact Host and browser Origin checks before delegation;
- no shell interpretation of capability URLs;
- bounded Singleserve-owned HTTP inputs and non-sensitive outputs;
- no release claim without real-browser and automated security evidence.

The fallback for a failed security design or mandatory candidate test is to keep the roadmap item blocked and not release v0.2.0. Re-enabling sessionStorage, weakening Host/Origin checks, sharing host cookies across ports, or documenting an unverified behavior as supported are not fallback options.

## Test plan

### Deterministic Go and JavaScript tests

- Prove independent 256-bit credentials and deterministic entropy-failure behavior.
- Prove bootstrap method/path/Host validation, atomic consumption, owner-controlled renewal, expiry/replay behavior, redirect target, cookie attributes, and security headers.
- Prove exact Host validation for IPv4, IPv6, `.localhost`, malformed authorities, case normalization, aliases, and configured addresses.
- Prove authentication-mode precedence and Origin policy for cookie, header, bearer, bootstrap, absent Origin, opaque/null Origin, duplicate headers, and mismatches.
- Prove all Singleserve credentials and query data are stripped before application delegation and never appear in response payloads or test failures.
- Prove control request bodies and identifiers are bounded, unsupported methods fail closed, and auth failures do not create tab or lifecycle state.
- Prove bootstrap consumption and simultaneous auth are race-free.
- Prove the client never accesses Web Storage, never returns a token, preserves caller headers, refuses cross-origin fetches, and retains heartbeat/reconnect/disconnect/shutdown behavior.
- Prove browser-opener commands never use a shell/command interpreter and never interpolate consumer-controlled text.

### Loopback integration and hostile sibling tests

- Run two Singleserve launches and a hostile sibling loopback server. Bootstrap one launch, visit the sibling, and prove the sibling receives no launch cookie and cannot set or replay one against either launch.
- Prove simultaneous launches, reload, manual launch recovery, programmatic authentication, and consumer handler composition over actual listeners.
- Probe DNS-rebinding-style Host aliases and cross-port Origins and prove rejection before consumer delegation.
- Exercise slow/incomplete headers, oversized headers/control bodies, idle connections, and shutdown drain to validate resource limits without breaking ordinary application requests.

### Real-browser release tests

- Run the repository-owned contract through pinned Playwright Chromium in automated CI. The runner OS is an implementation detail, local browser automation is optional, and extra engines/platforms are diagnostic unless a concrete compatibility finding makes them relevant.
- Assert that `localStorage`, `sessionStorage`, IndexedDB, Cache Storage, service workers, referrer capture, and the returned session object contain no reusable Singleserve credential. If the browser retains the consumed bootstrap URL in user-visible history, prove replay is rejected and document the browser behavior.
- Assert server-owned redirect to a clean URL occurs before application JavaScript, reload and a clean new tab work through the cookie, and two-tab/final-tab lifecycle semantics remain correct.
- Assert cross-origin and sibling-loopback attacks cannot read, receive, overwrite, or use the session credential.
- Assert a consumed/expired bootstrap URL cannot establish a new unauthorized session, then prove an owner-issued replacement establishes a clean session according to the final renewal contract.
- Assert unavailable-server and guarded-shutdown UI integration remains observable without exposing credentials.

### Security and repository gates

- Run `scripts/check.sh`, targeted race tests, `go vet`, coverage, client tests, example smoke, and `git diff --check`.
- Run the pinned vulnerability and static-analysis checks and record tool/database versions.
- Review CodeQL or equivalent findings, CI permissions, immutable action SHAs, generated module contents, and the release secret scan.
- Run `scripts/release-check.sh v0.2.0` only after the changelog/specification are release-ready and the worktree is clean. The script must not tag or publish.

## Acceptance criteria

- `connect()` performs no read or write through Web Storage or another script-readable persistence API.
- The browser-client result and exports contain no authentication capability or storage key.
- The first consumer-controlled response is served at a clean URL after a Singleserve-owned, non-cacheable, non-referring bootstrap transition; any unavoidable opener or history residue is non-replayable.
- Bootstrap, browser-session, and programmatic credential roles and lifetimes are explicit; replay behavior is bounded and tested.
- Reload and clean new-tab authentication use only an isolated HttpOnly, Secure, SameSite=Strict, non-persistent `__Host-` cookie.
- The supported launch origin prevents sibling loopback services on other ports or hosts from receiving, overwriting, or replaying the cookie.
- Every request has an accepted effective Host; unsafe cookie-authenticated browser requests require exact Origin; explicit programmatic auth cannot weaken browser rules.
- Application middleware receives no Singleserve query, cookie, token header, matching bearer value, bootstrap state, or credential-bearing `RequestURI`.
- Browser opener commands use no shell/command interpreter and observed launch arguments do not remain useful as a long-lived session credential.
- Control endpoints and HTTP server settings have tested method, body, identifier, header, timeout, idle, and non-echo bounds appropriate to Singleserve ownership.
- Heartbeat, health, fetch, tab tracking, reconnect observation, pagehide disconnect, unavailable notification, guarded shutdown, explicit lifetime, and browser-bound lifetime retain their specified outcomes.
- Unit, integration, race, fuzz-seed, hostile-sibling, real-browser, vulnerability, static-analysis, CI supply-chain, secret-scan, coverage, documentation, and release-policy gates all pass.
- No required security or browser gate is skipped and no known security finding within the supported threat boundary remains open. Out-of-boundary limitations and disproved findings are documented explicitly rather than accepted as release risk.
- v0.2.0 migration notes identify removal of `session.token`, `TOKEN_STORAGE_KEY`, sessionStorage fallback, browser token headers, and any changed launch/programmatic contract.
- No unrelated feature is included, and no tag or publication occurs without separate explicit authorization.

## Risks and fallback plan

- **`.localhost` interoperability:** RFC 6761 specifies special handling, while the canonical Playwright Chromium contract must demonstrate the required browser behavior. Investigate another engine or platform only when a concrete incompatibility is observed; if the supported design cannot meet the isolation contract, block the release.
- **Cookie `Secure` behavior on local HTTP:** browser exceptions differ. Test before selecting `Secure` or a cookie prefix; do not claim an attribute that a supported browser silently rejects.
- **Programmatic compatibility:** callers currently derive a reusable token from `Launch.URL()`. Provide an explicit replacement contract and migration notes; do not keep browser bootstrap reusable to preserve that pattern.
- **Custom addresses and IPv6:** per-launch host isolation may interact with user-selected binds. Preserve loopback-only safety even if some custom forms must be rejected or documented as incompatible with browser sessions.
- **Application compatibility:** removing `session.token` and browser token headers is breaking. Use v0.2.0, compile/example tests, and clear migration guidance rather than a weak compatibility switch.
- **Browser automation fragility:** pin a supported harness/browser channel and distinguish product failures from infrastructure failures. Infrastructure failure still blocks release until rerun; it does not waive the test.
- **Security-tool false positives or network freshness:** pin tools, record databases, triage findings explicitly, and keep networked evidence separate from deterministic offline checks.

There is no rollback to v0.1.0 credential behavior inside v0.2.0. If implementation cannot satisfy the plan, leave `security-hardening` Pending or Blocked and continue supporting only the accurately documented existing tag until a secure design is ready.

## Discoveries

- RFC 6265 explicitly states that cookies do not provide isolation by port. The v0.1.0 test named `TestLaunchCookiesDoNotCollideAcrossPorts` proves authentication selection but not cookie confidentiality from the other port.
- The v0.1.0 server sets the cookie on the consumer response, so application code can override security headers and runs before `connect()` scrubs the URL.
- The v0.1.0 browser header token is unnecessary for reload once the cookie exists, but the cookie's host scope must be fixed before relying on it as the sole browser credential.
- The WSL opener includes `cmd.exe /C start`, which conflicts with the repository invariant that browser URLs are never launched through a shell or command interpreter.
- `SECURITY.md` still predates the supported v0.1.0 tag and requires immediate documentation correction.
- Safari 26.5.2 is installed locally, but WebDriver requires an explicit persistent “Allow remote automation” setting. The repository must not silently change that setting or make local browser automation a development prerequisite. Repository-owned Playwright Chromium CI supplies the mandatory evidence; local WebDriver and other engines remain optional diagnostics.
- `govulncheck` v1.6.0 reported GO-2026-5856 against local Go 1.26.4 and no vulnerability after the module baseline moved to Go 1.26.5.
- SQLRise accepted a two-minute first-bootstrap requirement for `--no-open`: expiry requires owner restart, while successful bootstrap continues under explicit lifetime. This removes the need for a SQLRise renewal UI but does not remove the generic need to rotate after an immediate opener failure.
- The real-browser fixture's test guard initially denied every shutdown reason, which made its final-tab lifecycle assertion unreachable. The guard now denies only the explicit browser shutdown request under test and permits the separate browser-disconnected outcome.
- Chromium treats a renewed bootstrap URL opened from the existing failed bootstrap document as a same-document fragment navigation. The fixed bootstrap module must therefore handle `hashchange` and rerun its closure-and-scrub exchange; merely issuing a fresh server capability is insufficient for that natural recovery path.

## Decision record

- **2026-07-15 — Security over compatibility:** The user directed that security is absolute for Singleserve. v0.2.0 will not preserve a weaker Web Storage mode.
- **2026-07-15 — Security-only release:** v0.2.0 contains security hardening and its necessary migration, tests, docs, and tooling; unrelated features remain deferred.
- **2026-07-15 — Real-browser evidence is mandatory:** Browser authentication claims cannot be released based solely on Node mocks or an optional smoke test.
- **2026-07-15 — Per-launch origin mechanism:** use a 128-bit high-entropy `.localhost` host, exact Host validation, and a host-only cookie; reject configured loopback aliases outside `127.0.0.1`, `::1`, and `localhost`.
- **2026-07-15 — Bootstrap and programmatic API:** put an independent two-minute, atomically consumed bootstrap capability in the URL fragment and exchange it from a fixed Singleserve page; expose a launch-bound no-proxy `http.Client` carrying a separate private programmatic credential.
- **2026-07-15 — Owner-controlled bootstrap renewal:** expose `Launch.NewBootstrapURL()` to replace the single active unconsumed capability and reset its two-minute deadline. Renewal is explicit, leaves lifetime and established session state unchanged, and does not imply an automatic or consumer-facing renewal interface. SQLRise `--no-open` instead requires first bootstrap within two minutes and owner restart after expiry.
- **2026-07-15 — Cookie attributes:** retain loopback HTTP but require a host-only, HttpOnly, Secure, SameSite=Strict `__Host-` cookie. Supported browsers must accept it on the trustworthy `.localhost` origin and reject a sibling's `Domain=localhost` injection; otherwise v0.2.0 remains blocked. Local TLS remains outside v0.2.0.
